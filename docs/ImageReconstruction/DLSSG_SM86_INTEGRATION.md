# DLSSG SM86 frame-generation integration

Status: candidate integration, not release-certified. September 9 testing
isolated and corrected the mixed-runtime startup crash. The owner subsequently
confirmed working generation and HUD output; wider hardware, long-session and
latency measurement remain open.

## Multiplier, Reflex and HUD

Camera exposes 2x/3x/4x output, capped by the SDK's reported maximum and the
proxy configuration. DLSS-G receives the real image with HUD plus a separate
UI-color/alpha guide. FSR3 retains its separate UI-composite ownership.

DLSS-G automatically requests Reflex while generating. The optional NVIDIA
Reflex switch also requests it while generation is paused. Boost, marker
optimization and the limiter route to the active DX12 instance; DX11 Reflex
remains suppressed so two instances do not pace the same frame. FSR3 continues
to own its pacing and does not expose the DLSS-G Reflex controls.

UI availability checks the SDK's `lowLatencyAvailable`, not just the presence
of a plugin DLL. The standalone RTX 3060 Ti test confirmed availability,
normal/boost/off options, limiter options and sleep calls, with both Streamline
instances loaded. This does not measure end-to-end game latency. The cap is in
rendered frames per second, not multiplied output FPS.

PIXL exposes a `Frame generation backend` selector beside the existing
frame-generation control:

- `AMD FSR 3` uses PIXL's existing FidelityFX presentation path.
- `DLSSG (SM86 / version.dll)` uses a native DX12 swap chain and a separate
  Streamline DX12 instance. This allows `version.dll` from
  `sdli1995/dlssg_for_sm86` to intercept the DLSS-G runtime while PIXL still
  owns reconstruction, depth, motion and UI composition.

The selector is serialized as `ImageReconstruction.frameGenerationBackend` and
requires a Skyrim restart because the presentation backend is selected while
the swap chain is created.

## Runtime files

For the DLSSG option, place the SM86 proxy files beside the actual Skyrim
rendering executable as described by the upstream project:

- `version.dll`
- `dlssg_sm86.ini`

PIXL's separate `Data/Shaders/ImageReconstruction/StreamlineDX12` runtime directory must also contain the matching
Streamline files (`sl.interposer.dll`, `sl.common.dll`, `sl.dlss_g.dll`, and
the Reflex/PCL plugins) and `nvngx_dlssg.dll`. All five Streamline DLLs must
have matching versions. The tested package is the official NVIDIA 2.10.3
release, staged under `pipeline/ImageReconstruction/Kernels/ImageReconstruction/StreamlineDX12`
with its license notices. NGX has its own version scheme; do not compare its
version to Streamline. These third-party binaries are not generated by PIXL's
C++ build. If the DX12 Streamline feature
is absent, PIXL reports DLSSG unavailable and leaves FSR3 unaffected.

The two frame-generation paths are mutually exclusive. PIXL never dispatches
FSR3 and DLSSG for the same present, avoiding double interpolation and keeping
the existing raw depth/motion guide contract intact.

## Sidecar ownership

The presentation backend is selected once, while Skyrim creates its swap
chain, and remains fixed for the process lifetime:

- TAA, FSR upscaling, DLSS and DLAA retain Skyrim's native D3D11 swap chain.
- FSR3 frame generation owns a two-buffer FidelityFX D3D12 sidecar.
- DLSSG owns a three-buffer native D3D12 sidecar upgraded only by the separate
  DX12 Streamline instance.
- Neural Rendering without frame generation owns a two-buffer native D3D12
  sidecar and does not initialize either frame-generation presenter.

DLSSG feature support is queried only after binding a real D3D12 device. The
native device is retained for NGX and resource creation; a separate wrapper
handles presentation-queue creation. The DXGI factory is upgraded before
creating the swap chain. The earlier raw-factory workaround was rejected:
the creation crash reproduced outside Skyrim with the mismatched DLL set and
did not reproduce with a coherent 2.10.3 set. A failed DLSSG probe or version
validation leaves the ordinary D3D11 renderer active.
The D3D11 Streamline instance is never allowed to wrap the FidelityFX sidecar
or the D3D11-facing PIXL proxy.

DLSS-G state is queried on the presentation thread. Its input-completion fence
is queued before PIXL signals the shared fence that releases the next D3D11
frame, protecting guides and UI from premature reuse. Command allocators also
wait for their own previous GPU submission before CPU reset, with a bounded
timeout. Failed tags disable interpolation for that frame.

## Validation

The Release build and D3D11 RCAS regression tests pass. `tools/SidecarSmoke.cpp`
reproduced the mixed-runtime startup failure and passed initialization, three
FG-off presents, and shutdown using a coherent runtime, including simultaneous
DX11/DX12 Streamline instances. Skyrim subsequently passed its first Present
and remained responsive with DLSS-G selected. These checks do not prove
interpolation, image quality, or frame pacing. Runtime validation remains
required on an RTX 30-series card. First verify a normal
world load with frame generation and Neural Rendering disabled. Then test FSR3
and DLSSG in separate restarts, verifying the upstream `dlssg_sm86` logs and
checking menus, interiors, HDR, loading transitions and frame pacing.

Build the standalone diagnostic with `tools/BuildSidecarSmoke.cmd` from the
repository root. Run `build/SidecarSmoke.exe <game-directory> <DX12-runtime-directory> --dual`.
It loads the installed SM86 proxy and vendor runtime; it does not load Skyrim
or compile any Skyrim shaders. Run it with the game closed to avoid sharing GPU
resources during gameplay. `tools/TestPixlSidecarRuntime.ps1` validates runtime
version coherence and prints SHA-256 hashes; the staging script also invokes it.
